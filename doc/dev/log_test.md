# 日志压力测试 (log_test)

本文档记录日志写入的压力测试与参数实验. 测试脚本位于 `test/log/`, 需求与设计见
[log.md](log.md), 防御限制见 [limit.md](limit.md).

## 测试方法

压力测试脚本 `test/log/stress.js` 生成含多个 service 的临时配置, 用 release
二进制启动 `pm-sysd-init --machine`, 并发启动所有 service 持续向 stdout/stderr
输出日志, 再对比各 service 实际产出与 sqlite 入库情况, 观察日志写入, 丢弃,
内存占用与吞吐.

脚本用法, 场景定义, 选项与结果解读见
[test/log/README.md](../../test/log/README.md), 此处不重复.

基准测试使用脚本默认选项 (默认配置与默认值) 完整运行四类测试, 即 `--type=all`:
default 全速, tune 缓冲调优, long 超长单行, rate 限速搜索.

Linux 用默认内存采样间隔 `--sample-ms=200`, Windows 上每次采样需启动一次
powershell, 改大 `--sample-ms=1000`.

### 平台对比

- 无损写入速率: Linux 14.7MB/s (约 19 万条/s) 约为 win10 4.9MB/s (约 6.3 万条/s)
  的 3 倍.
- 单 service 全速入库吞吐: Linux 185,699 条/s (13.0MB/s) 约为 win10 59,747 条/s
  (4.1MB/s) 的 3 倍.
- 全速多 service 丢弃率量级相近: Linux 89.1%~96.6%, win10 93.3%~95.9%.
- 缓冲调优两机均无明显收益, 丢弃率与默认 s8 基本持平.
- 超长行入库字节吞吐 Linux 196.3~216.8MB/s, 略高于 win10 143.6~181.8MB/s.
- init RSS 峰值 Linux 明显更高: 默认 s16 115.8MB, tune b2 121.5MB, 对比 win10 的
  s16 65.7MB, tune b8 73.0MB.

### 误差分析

- 每场景单次运行, 未重复取平均, 短行高并发与 rate 限速搜索波动较大,
  精确数值仅作量级参考.
- 两机采样间隔不同 (Linux 200ms, win10 1000ms), win10 采样点少, RSS
  峰值可能漏采.
- 测试子进程与 init 同机运行, 并发场景相互争抢 CPU 与磁盘.
- 两机硬件规格不同 (8 核/16GB 对比 4 核/8GB), 平台对比包含硬件差异,
  不完全等于软件差异.
- 临时目录与数据库位于磁盘 (非 tmpfs), 磁盘写入带宽是变量之一.

## 参数实验

以下实验于 2026-11-20 完成, 当时代码默认值为 `SYSD_LIMIT_LOG_PENDING_BYTE` 5MB,
`SYSD_LIMIT_LOG_PENDING_N` 1 万, `SYSD_LIMIT_LOG_CHANNEL_CAPACITY_N` 100.

部分实验在 `--no-index` 基础上进行, 每场景 10 秒 (`--duration=10`).
表内按当时记录方式给出, 部分表只记录一种吞吐单位 (条/s 或 MB/s), 内存 (RSS)
仅在部分实验有记录.

这些实验的结论后来被采纳, 成为现在的默认值.

### sqlite 调优实验 (失败已回退)

曾尝试给 sqlite 日志写入加 `PRAGMA journal_mode = WAL` 与
`PRAGMA synchronous = NORMAL`, 期望减少每次提交的 fsync 开销.
在两台机器上重跑压力测试后, 结果反而明显回退:

- 长行字节吞吐约减半: Linux 161~176MB/s 降到 81~88MB/s, Windows 127~144MB/s 降到
  73~83MB/s.
- 短行入库吞吐下降约 10~30%.
- Linux 无损速率从约 3.6MB/s 降到约 873KB/s, Windows 基本不变 (约 477KB/s).

原因是本项目使用单一共享 sqlite 连接 (单写者线程, 互斥锁串行), WAL
的读写并发优势 用不上, 反而多了 WAL 写入后再 checkpoint 回主库的双写开销. 而
fsync 本就不是主要瓶颈: 短行受每行 INSERT 与索引维护限制, 长行受页写入带宽限制.
因此已回退.

### 重要发现

- 短行写入瓶颈是索引维护, 关闭索引后丢弃率大幅下降.
- Linux 提高 `SYSD_LIMIT_LOG_PENDING_N` (1 万到 10 万) 有效,
  再高收益递减且耗内存, Windows 无效甚至略差.
- 两机限速无损速率都随 `SYSD_LIMIT_LOG_CHANNEL_CAPACITY_N` 上升, 1000 时最高,
  且几乎不增加峰值内存.
- 上述结论成为调大默认值的依据 (PENDING_N 1 万到 10 万, 通道容量 100 到 1000).
